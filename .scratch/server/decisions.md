# Server: decisions log

Grilling "server by the contract" (backend session, 2026-10-06), after
[handoff.md](handoff.md). One entry per answered question; open questions stay out of this file
until the user answers them. The spec this produces is `spec.md` next to this file.

## Round 1

- **Q1** Remaining time not stated. Suggested roles (`fromCvId`) go in the last ticket, so they can
  be cut without touching the rest (root architecture §12 cut order).
- **Q2** Generation job and attempt are two tables, as the glossary already says.
  `generation_jobs` — one row per generation the user started (a CV created or a manual Retry),
  `id` = BullMQ jobId; `cv_id → cvs on delete set null`, so deleting a CV does not take its jobs
  with it; `user_id → users cascade`. `generation_attempts` — one row per attempt (model, prompt
  version, agent steps, tokens, ms, error), `job_id → generation_jobs cascade`. Automatic retries
  are BullMQ's own (`attempts: 3`, exponential backoff from 5 s) on the same job.
- **Q3** The JWT secret is generated on the first api start and kept in Postgres (`app_secrets`,
  `insert … on conflict do nothing`, then read), so `docker compose up` needs nothing but
  `ANTHROPIC_API_KEY` and sessions survive a restart. `JWT_SECRET` in the env overrides it (tests).
- **Q4** The fake model exists only in tests, swapped in through the DI token of the model factory
  (`agents/llm.ts`). No runtime switch: a missing key still stops compose.
- **Q5** e2e tests use Postgres and Redis from `backend/compose.yaml` (published on `127.0.0.1`):
  a separate `cv_test` database and BullMQ prefix, migrations once per run, tables truncated
  between tests; without them the run fails with a clear message. Unit tests of pure functions need
  neither.
- **Q6** Scaffold: NestJS 11, CommonJS, `nest build` with SWC, `tsc --noEmit` for typecheck, Vitest
  + `unplugin-swc` + supertest, oxlint, prettier. Own `ZodValidationPipe` and error filter (the
  `{ error: { code, message, details } }` shape), no `nestjs-zod`. Drizzle migrations generated by
  `drizzle-kit generate`, committed, applied by the api on start with `migrate()`. The env is
  parsed by a Zod schema; a bad env stops the process at start.
- **Q7** Model `claude-sonnet-5-5` by default (`ANTHROPIC_MODEL`). Timeouts: 120 s per model call,
  300 s per attempt (60/180 s was too tight for a 20 000-char source); BullMQ lock duration above
  the attempt timeout. Worker concurrency 4 (env).

## Round 2

- **Q8** The hourly answer limit is cut: it was there for the AnswerAgent's model call, and an
  answer written as is costs nothing. The hourly generation limit stays (it guards the key's
  money). Known simplification for the README. Contract change → root ticket (Q10).
- **Q9** Lost queue jobs are recovered on worker start **and** every 60 s: CVs in
  `queued`/`generating`/`retrying` with no live BullMQ job are re-enqueued with the same jobId.
  `POST /api/cvs` answers `202` even if `add()` throws (logged). On a stalled re-run, the job's
  attempt rows still `running` are closed as `failed` (`stalled`).
- **Q10** One root ticket (docs + shared) carries what this grilling changes in root-owned files:
  `docs/cv-statuses.md` §4/§5 (job vs attempt tables) and its `docs/uk` copy, the answer limit
  out of `usageResponseSchema` and `api.md`, the frontend mocks. It blocks only the server's
  `/api/usage` ticket.
- **Q11** Tickets are vertical slices, each checked by the frontend without mocks on
  `pnpm stack`: 1 scaffold · 2 auth · 3 intake · 4 CVs without generation · 5 generation happy
  path · 6 verification (never cut) · 7 failures, Retry, recovery · 8 answer/skip · 9 PATCH ·
  10 PDF · 11 usage + hourly generation limit · 12 `fromCvId` (last, cut first).
- **Q12** Logs: pino (`nestjs-pino`) to stdout, JSON. requestId, userId, cvId, jobId on each line;
  LLM errors in full; never `source_text`, answers or passwords.

## Round 3 — questions and the agent

- **Q13** The auto question about the whole `experience` block creates a new experience item on
  answer: each non-empty line becomes a bullet; title, company and period stay empty for the
  editor. Its text in all six languages asks for the most recent job, one point per line, and says
  the title, company and dates go in the editor. Root ticket (shared texts, root §6.5).
- **Q14** A `text` answer to the whole `skills` block is split on `,` `;` and line breaks, trimmed
  and appended as separate skills without duplicates or the `label` prefix. `"{label}: {value}"`
  stays only for a `choice` that targets `skills`. Root ticket.
- **Q15** `applyAnswer` moves into `@cv/shared` (pure, tested); the server and the frontend mocks
  import the same function. Root ticket; the server's answer/skip ticket waits for it.
- **Q16** The model fixes a rejected draft by sending the whole `submit_draft` again — one tool,
  one schema; the last schema-valid submission is always a full draft.
- **Q17** `claude-sonnet-5-5` rejects forced tool use, so `toolChoice` is `'auto'` and the
  instructions require answering only through `submit_draft`. `stopWhen: [accepted,
  isStepCount(3)]`; a step without a tool call also ends the loop. The attempt's result is the
  last schema-valid submission after `sanitise`; none → `LLM_INVALID_OUTPUT` (retryable).
- **Q18** SDK retries stay on inside a step (`maxRetries: 2`, within `stepMs`), so a short 529 on
  step 2 keeps step 1; BullMQ retries what is left. Classification: `RetryError`/`APICallError`
  retryable (408, 409, 429, ≥ 500, network) → `LLM_UNAVAILABLE`; `TimeoutError` → `TIMEOUT`;
  401/403 → `LLM_CONFIG`, other 4xx → `INTERNAL`, both not retried; no valid submission →
  `LLM_INVALID_OUTPUT`, retried.
- **Q19** Strict tools off: the schema with its limits is checked locally by Zod and its errors go
  back to the model. Request-level automatic prompt caching on; cache read/write tokens are stored
  on the attempt.
- **Q20** `maxOutputTokens` 16 000 per step (thinking can't be turned off on this model). `stage`
  is written from SDK hooks — `onStepStart` step 0 → `drafting`, `onToolExecutionStart` →
  `verifying`, `onStepEnd` with `accepted: false` → `revising`, after the loop → `saving` —
  best effort with a log, since the SDK swallows hook errors.
- **Q21** Over the cap of 12 open questions, they are kept in this order: auto (required fields) →
  `confirm` (≤ 5) → the one `multi` → model (≤ 7, in the model's order). A model question about a
  field that also has an auto question replaces the auto one.
- **Q22** A source that doesn't look like a CV is not a failure: the draft comes out nearly empty,
  auto questions ask for the required fields, the CV is `needs_input`. No new error code.
- **Q23** The prompt is static first, dynamic last, which is also the cache prefix: `submit_draft`
  definition → `instructions` (rules + a static example; nothing that changes per CV) — cache
  breakpoint — one user message: `<source>`, `<user_facts>`, `<target_role>`, `<role_context>`,
  `<cv_language>`, `<today>` — cache breakpoint. `PROMPT_VERSION` is a hash of the static part.
  A test checks that `instructions` hold no byte of user data and are identical for two CVs.
- **Q24** One file per tool: `agents/draft/tools/<name>.tool.ts`, a factory that takes the
  attempt's context (`createSubmitDraftTool({ source, facts })`); the system prompt and the example
  have their own files under `agents/prompt/system/`.
